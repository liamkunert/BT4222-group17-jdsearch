# Beyond Generic Baselines: Dataset-Specific Insights for Your Project

As you dive into your projects, it can be tempting to rely on generic machine learning tutorials or standard collaborative filtering baselines. However, the difference between a good recommendation model and a great one lies in how well you understand the physical reality, structural quirks, and hidden richness of your specific dataset.

To help you get started, I've put together an inspiration list for those of you working with the **JDSearch** and **MIND** datasets. I strongly encourage you to move beyond basic ID-matching and standard theories. Take a close look at the specific characteristics, missing data realities, and rich metadata outlined below, and think about how you can engineer features or design architectures that actually leverage them.

If you prefer working on other datasets rather than JDSearch or MIND, that is completely fine as long as your dataset matches the project requirements. The following insights can still inspire how you approach and explore the data in your own chosen datasets.

Here are some dataset-specific insights to consider for your modeling:

---

## JDSearch Data

### 1. No Global Timestamps
The dataset only has `history_time_list` (relative intervals between clicks, e.g., 12 seconds, 4 seconds). There is no global timestamp, so a chronological temporal cutoff across all users is physically impossible.

### 2. No User IDs
The dataset consists of anonymous session rows. You cannot track a user across multiple test queries, meaning traditional Matrix Factorization based on a `user_id` embedding is impossible.

### 3. Missing Metadata for Certain Products
The documentation explicitly warns: *"Noticing that there exists some missing products in our dataset, `product_meta_data.txt` doesn't contain metadata about these products."* Students must design models that handle historical items missing their brand, name, or category.

### 4. Differentiating Active vs. Passive Intent
The `history_qry_list` uses `-1` for interactions that occurred without a search query (e.g., clicking on the homepage or recommendations). Differentiating between active searching and passive browsing is a massive behavioral signal.

### 5. The "Follow" (FLW) Interaction
The dataset tracks 4 historical interaction types (**ORD**, **CLICK**, **CART**, and **FLW**). Students may not just focus on clicks and purchases, but also model the specific intent behind a "Follow".

### 6. One-to-Many Search Sessions
The dataset notes: *"if a user interacted with multiple products under a one query, these behaviors will be separated to multiple interactions."* History sequences will frequently feature duplicated queries side-by-side. Sequence models (like Transformers) must be built to handle these repeated query states.

### 7. The Product Name (`name`)
Do not ignore the `name` column (anonymized term IDs of the product title). Because this is a Search dataset, the single most important feature is calculating the text relevance (e.g., BM25, vector similarity) between the query term IDs and the product name term IDs.

### 8. 4-Level Category Depth
The dataset provides exactly 4 levels of categories (`cate_id_1` through `cate_id_4`). Students may consider how to leverage the difference between a broad L1 category match versus a highly specific L4 category match.

## MIND Dataset

### 1. Pre-trained Knowledge Graph Embeddings
MIND explicitly provides `entity_embedding.vec` and `relation_embedding.vec`, which are 100-dimensional dense vectors trained using TransE on the Wikidata knowledge graph. These provided graph embeddings allow a model to understand that two articles are highly related if they contain entities like "Tim Cook" and "Apple"—even if the overlap is technically zero.

### 2. Time-of-Day and Day-of-Week Context
The `behaviors.tsv` file contains a highly granular Time column for every single impression event (e.g., `11/15/2019 10:22:32 AM`). Time could be used as an active input feature. News consumption is highly cyclical; a user's intent on a Tuesday morning (e.g., finance, quick news) is often drastically different from a Sunday evening (e.g., long-form features, entertainment).

### 3. Entity Linking Confidence Scores
The entity data in `news.tsv` isn't a flat list. It is a rich JSON structure that includes a Confidence score (e.g., `1.0`) generated by the NLP entity-linking algorithm. So we may not treat all extracted entities as ground truth. In reality, entity extraction is noisy. Models can use these confidence scores to dynamically filter out weakly-linked entities or apply attention weights.

### 4. Entity Positional Prominence (Occurrence Offsets)
The entity JSON also includes `OccurrenceOffsets`, tracking the exact character index where the entity appears in the text. The structural location of an entity dictates its importance. An entity mentioned at the very beginning of a title (offset 0) is usually the primary subject of the article, whereas an entity mentioned at the very end of an abstract is often peripheral context.

### 5. Entity Ontological Types
The entity JSON includes a Type field (classifying the entity as a Person, Organization, Location, etc.). A user might have a strong behavioral tendency to follow specific People (e.g., celebrities, politicians) but no specific allegiance to Locations. Separating entity overlap/similarity by their ontological Type is a powerful modeling technique supported by the data.
